# 5. 데이터베이스(DB) 및 파일 스토리지 구조 명세서

## 5-1. 아키텍처 개요
본 애플리케이션은 사용자 개인정보 보호 및 오프라인 접근성을 고려하여 **온디바이스 기반의 로컬 DB (SQLite)**와 **앱 전용 파일 스토리지**를 주력으로 사용합니다. 개인 데이터 및 원본 이미지는 기본적으로 단말 내부에 저장하고, 서버에는 중복 분석 방지를 위한 최소한의 캐시 데이터만 유지함으로써 클라우드 서버에 저장되는 사용자 데이터의 범위를 최소화하였습니다.

---

## 5-2. 로컬 데이터베이스 (SQLite) 스키마 구조
기기 내에 저장되는 `soseng.db`는 추출된 비정형 데이터를 유연하게 담을 수 있도록 **동적 Key-Value (JSON) 구조**를 채택했습니다.

### 테이블 명세: `screenshots` (클라이언트 기기 로컬 DB)

| 컬럼명 | 타입 | 제약 조건 | 설명 |
| :--- | :--- | :--- | :--- |
| **`id`** | INTEGER | PRIMARY KEY, AUTOINCREMENT | 로컬 DB 내 고유 식별자 |
| **`asset_id`** | TEXT | | 갤러리 원본 에셋과 매핑하기 위한 고유 ID |
| **`type`** | TEXT | NOT NULL | 카테고리명 (`SCHEDULE`, `PLACE`, `WISHLIST`, `MEMO`) |
| **`confidence`** | REAL | | 온디바이스(Vision/Regex) 분류 시점의 신뢰도 점수 |
| **`fields`** | TEXT | (JSON 포맷) | LLM 또는 정규식으로 추출된 데이터를 동적 Key-Value 형태의 JSON 문자열로 저장 |
| **`image_path`** | TEXT | | 앱 내부 스토리지에 저장된 이미지 파일의 경로를 기록 |
| **`status`** | TEXT | DEFAULT 'DRAFT' | 데이터 확정 상태 (`DRAFT`: 분석 직후, `CONFIRMED`: 최종 승인) |
| **`created_at`** | TEXT | DEFAULT CURRENT_TIMESTAMP | 레코드 생성 일시 |
| **`updated_at`** | TEXT | DEFAULT CURRENT_TIMESTAMP | 레코드 최근 수정 일시 |

> [!TIP]
> **설계 의도 (Trade-off): 왜 `fields`를 JSON 텍스트로 저장했는가?** 
> 카테고리(`type`)별로 추출되는 속성의 종류가 서로 다르고 향후 필드가 추가될 가능성이 있으므로, 가변적인 추출 결과는 JSON 형태로 저장하였습니다. 모든 속성을 고정된 컬럼으로 관리할 경우 새로운 정보 항목이 추가될 때마다 스키마 변경 및 Migration이 필요하지만, JSON 구조를 채택함으로써 기존 스키마 변경 없이도 다양한 형태의 결과를 저장할 수 있습니다. 
> 다만, 개별 JSON 필드에 대한 복잡한 검색이나 정렬 쿼리에는 정형 컬럼 방식보다 불리할 수 있으나, 본 애플리케이션의 주요 데이터 접근 방식인 '레코드 단위의 개별 상세 조회'에는 적합하도록 설계하였습니다.

## 5-3. 파일 스토리지 및 DB 매핑 구조

사용자가 이미지를 분석 요청하면, 원본 이미지가 앱의 보호된 내부 스토리지 영역(`ApplicationDocumentsDirectory`)으로 안전하게 복사되어 보관됩니다.

### 1) 로컬 디렉토리 계층 구조
모든 이미지는 분석된 카테고리(`type`)별로 분류되어 폴더에 나뉘어 저장됩니다.

```text
📁 /data/user/0/com.soseng.app/app_flutter/ (Android 기준 AppDocDir)
 └── 📁 AppStorage/
      ├── 📁 SCHEDULE/
      │    └── image_20260901_1234.jpg
      ├── 📁 PLACE/
      ├── 📁 WISHLIST/
      └── 📁 MEMO/
```

### 2) DB ↔ 파일 매핑 구조
각 `screenshots` 레코드는 `image_path` 컬럼을 통해 해당 이미지 파일을 참조합니다.

- **저장:** 갤러리 이미지 선택 ➡️ 온디바이스 분석을 통해 카테고리 식별 ➡️ 카테고리 폴더로 이미지 복사 ➡️ DB에 추출된 데이터와 함께 앱 내부 스토리지 경로(`image_path`)를 INSERT
- **조회:** 사용자가 앱 리스트에 진입 시 로컬 DB를 조회하여, DB가 참조하는 경로(`image_path`)의 이미지를 화면에 렌더링합니다.

### 3) 데이터 저장 및 삭제 Lifecycle
사용자가 저장된 데이터를 삭제하는 경우, 해당 DB 레코드(DELETE)와 더불어 연결된 실제 이미지 파일을 파일 스토리지에서도 함께 삭제하여 불필요한 파일이 앱 내부에 잔존하지 않도록 관리합니다. 이를 통해 DB에 존재하지 않는 잉여 이미지 파일이 남거나, 삭제된 이미지에 대한 DB 참조가 유지되는 고아(Orphan) 데이터를 방지합니다.

## 5-4. 백엔드 서버의 임시 분석 결과 Cache

백엔드 서버(FastAPI) 역시 동일한 형태의 SQLite `screenshots` 테이블을 보유하고 있으나, 데이터베이스의 성격과 활용 목적이 완전히 다릅니다.

- 서버 DB는 사용자의 서비스 데이터를 영구 저장하기 위한 저장소가 아니라, **동일 이미지에 대한 반복적인 LLM 분석 요청을 방지하여 API 호출 비용과 처리 시간을 줄이기 위한 캐시(Cache)로 활용**합니다.
- 서버 DB는 원본 이미지 경로나 사용자의 식별 정보 대신, 익명화된 이미지 고유 해시값(`image_hash`)을 저장하여 캐시 히트(Cache Hit) 여부만을 판단합니다.
- *(한계점: 향후 LLM 모델 업그레이드나 프롬프트 변경 시, 기존에 캐싱된 분석 결과의 유효성을 새롭게 갱신/판단할 수 있도록 모델 및 프롬프트 버전 관리 체계를 도입할 필요가 있습니다.)*

## 5-5. 확장성 및 개인정보 보호

### 1) 확장성을 고려한 데이터 관리
본 아키텍처는 데이터의 성격에 따라 저장 영역과 형식을 명확히 분리하여 향후 기능 확장에 유연하게 대응할 수 있도록 설계되었습니다. 
무거운 이미지 원본은 **파일 스토리지**에서 폴더 기반으로 격리 관리하고, 이미지와 추출 결과의 메타데이터 관계는 **로컬 SQLite**에서 관리하며, 수시로 바뀔 수 있는 가변적인 추출 필드는 **JSON 포맷**으로 저장합니다. 따라서 향후 새로운 카테고리나 추출 필드가 추가되더라도, 기존 DB 스키마 구조나 파일 스토리지 로직의 변경을 최소화할 수 있습니다.

### 2) 클라우드 노출을 차단한 개인정보 보호
본 시스템은 사용자 데이터의 주 저장소를 단말로 두고, 이미지와 구조화 데이터의 역할을 분리하여 관리합니다. 추출 결과를 저장하는 주체는 서버가 아닌 사용자 단말이므로 클라우드 해킹이나 데이터 유출 위협으로부터 원천적으로 안전합니다. 서버는 오직 일회성 LLM 분석을 돕고 중복 요청을 방지하는 휘발성/비식별(해시) 역할로만 제한함으로써, 데이터 보안과 시스템 확장성이라는 목적을 동시에 달성했습니다.
