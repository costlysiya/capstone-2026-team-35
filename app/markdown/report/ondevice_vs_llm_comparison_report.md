# 정보 추출(Extraction) 성능 비교: 온디바이스 vs LLM

> [!TIP]
> 최종 보고서 작성을 위해 현재 프로덕션 환경(최신 프롬프트 및 Structured Outputs 적용) 기준으로 총 40건의 샘플을 Field-level Precision(정밀도) / Recall(재현율) 방식으로 분석한 결과입니다.

## 1. 평가 개요
- **목적:** 순수 온디바이스 처리(정규표현식)와 클라우드 기반 LLM 처리 간의 정보 추출 성능을 항목별(Field-level)로 정밀 비교하여, 본 프로젝트의 2단계 하이브리드 아키텍처(온디바이스 분류 ➡️ LLM 구조화 추출) 설계의 타당성을 검증합니다.
- **데이터셋:** 직접 수집한 영수증/티켓/예약문자 등 실제 사용자 OCR 텍스트 40건
- **비교군:**
  - **비교군 1 (온디바이스 Regex):** 기기 내 정규표현식 및 단순 텍스트 패턴 매칭
  - **비교군 2 (LLM):** `gpt-4o-mini` 모델 + Pydantic Structured Outputs (서버 연동)
- **정답지(Ground Truth):** `gpt-4o` 모델을 이용하여 참조 정답 데이터(Reference Ground Truth)를 생성한 후 자동 채점. 
  *(한계점: 본 연구에서는 정답 데이터 구축에 LLM을 활용하였으므로, 향후 연구에서는 사람이 직접 검수(Human-annotated)한 Ground Truth와의 비교를 통해 평가 신뢰도를 추가적으로 확보할 필요가 있습니다.)*

---

## 2. 추출 정확도 비교 (Field-level Precision / Recall / F1)

단순히 전체 문서 중 몇 건을 맞혔는지가 아니라, 개별 정보 항목(Field) 단위로 '얼마나 정확하게 추출했는지(정밀도)'와 '놓친 항목 없이 얼마나 잘 찾아냈는지(재현율)'를 면밀히 분석했습니다.

| 추출 항목 (Field) | Regex Precision | Regex Recall | Regex F1 | LLM Precision | LLM Recall | LLM F1 |
|:---|---:|---:|---:|---:|---:|---:|
| **날짜 (Date)** | 57.1% | 72.7% | **64.0%** | 84.6% | 100.0% | **91.7%** |
| **가격 (Price)** | 100.0% | 100.0% | **100.0%** | 100.0% | 57.1% | **72.7%** |
| **장소/상호명 (Place)** | 14.3% | 5.0% | **7.4%** | 50.0% | 80.0% | **61.5%** |
| **상품명 (Product)** | 100.0% | 20.0% | **33.3%** | 93.3% | 93.3% | **93.3%** |

### 정밀 분석 및 시사점
- **숫자/정형 데이터 (가격)**: 정규표현식(Regex)은 정형화된 숫자와 화폐 단위 패턴을 포착하는 데 최적화되어 있어 **100%의 압도적인 성능(Precision/Recall 모두 완벽)**을 보입니다. 오히려 LLM은 일부 데이터에서 숫자 범위를 놓치거나 쉼표 단위를 오인하는 등의 한계(Recall 57.1%)가 존재합니다.
- **비정형 엔티티 데이터 (장소, 상품명)**: 반면 '장소'나 '상품명' 같이 정해진 패턴이 없는 복잡한 엔티티(Entity) 추출에서는 Regex가 문맥을 파악하지 못해 철저히 실패(Recall 5% - 20% 수준)합니다. 반대로 **LLM은 문맥을 정확히 이해하여 장소와 상품명 추출에서 80% - 93% 이상의 높은 재현율(Recall)**을 발휘합니다.

## 3. 처리 성능 (속도 및 비용) 비교

| 평가 지표 | 온디바이스 (Regex) | LLM (gpt-4o-mini) | 비교 요약 |
|:---|:---:|:---:|:---|
| **평균 처리 소요 시간** | **0.17 ms** | 1.32 초 | 온디바이스가 **약 7,500배 이상** 빠름 |
| **건당 평균 사용 토큰** | N/A | 1,667 tokens | LLM은 입출력 토큰량에 비례해 비용 증가 |
| **건당 예상 서버 비용** | **0원 (무료)** | 약 15원 ($0.01) | 통신 및 과금 등 운영 환경 차이 극명 |

## 4. 종합 결론 및 시사점

> [!IMPORTANT]
> 본 Field-level 정밀 분석 결과, 본 앱의 **"온디바이스(빠른 카테고리 1차 분류) ➡️ 서버 LLM(비정형 데이터의 2차 추출)"**이라는 2단계 하이브리드 설계가 기술적으로 합리적인 구조임을 정량적으로 뒷받침합니다.

### 4-1. 분석 결과의 종합 시사점

본 실험을 통해 정보 추출 방식에 따라 처리 가능한 정보의 유형과 성능 특성이 상이함을 확인하였습니다. 정형화된 숫자 데이터인 가격 정보에서는 온디바이스 Regex가 Precision과 Recall 모두 100%의 높은 성능을 보였으며, 별도의 서버 통신 없이 0.17ms의 매우 짧은 시간 내 처리가 가능하였습니다. 반면 장소 및 상품명과 같은 비정형 Entity 추출에서는 Regex의 F1 Score가 각각 7.4%, 33.3%에 그친 반면, LLM은 각각 61.5%, 93.3%를 기록하여 문맥 기반 정보 추출에서 우수한 성능을 보였습니다.

이러한 결과는 온디바이스 방식과 LLM 방식 중 하나를 일괄적으로 선택하기보다, 정보의 특성에 따라 처리 방식을 분리하는 것이 효과적임을 시사합니다. 즉, 가격과 같이 규칙성이 높은 정보는 온디바이스에서 우선 처리하고, 장소·상호명·상품명과 같이 복합적인 문맥 이해가 요구되는 비정형 정보에 대해서는 서버 LLM을 활용함으로써 추출 정확도를 확보할 수 있습니다.

또한 LLM은 온디바이스 방식에 비해 높은 추출 성능을 제공하는 반면 평균 1.32초의 처리 시간과 건당 약 15원의 비용이 발생하므로, 모든 입력을 무분별하게 서버로 전송하는 방식은 서비스 규모가 증가할수록 비용 및 지연시간 측면에서 불리할 수밖에 없습니다. 

결론적으로, 기기단(온디바이스)에서 무료이면서 매우 빠른 속도(0.17ms)로 데이터의 카테고리를 즉각 판단하고 단순 정보를 걸러낸 뒤, 복합적인 문맥 이해가 요구되는 비정형 정보(장소, 상호명, 상품명 등)에 한해서만 선별적으로 서버 LLM으로 전송하여 Pydantic 스키마 기반으로 일관된 구조의 데이터로 변환하는 현재의 시스템 설계는 정확도와 시스템 효율성(속도/비용)을 동시에 고려한 합리적인 설계 방향임을 확인하였습니다.
