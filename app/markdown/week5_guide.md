# 🚀 5주차 개발 가이드라인: 비동기 큐, 실시간 상태 연동 및 API 고도화

4주차까지 배치 처리, 캐싱, 동시성 제한, 타입 정밀화, 마스킹 처리 등 서버의 핵심 비즈니스 로직을 모두 완성했습니다.
5주차는 **"사용자 경험(UX) 극대화"** 와 **"대용량 데이터 처리 안정성"** 에 초점을 맞춥니다. 앱에서 백그라운드로 사진을 분석하고, 진행률을 실시간으로 보여주며, 쌓인 데이터를 효율적으로 조회하는 기능을 구현합니다.

---

## 📌 5주차 핵심 목표 (비전)

1. **완벽한 백그라운드 처리**: 사용자가 앱에서 20장의 사진을 넘기며 1차 초안(온디바이스)을 보는 동안, 서버는 뒤에서 조용히(비동기 큐) 정밀 분석을 수행합니다.
2. **실시간 진행률 피드백**: "항목별 5~15초 내 업데이트" 목표를 달성하기 위해, 분석 상태를 앱이 주기적으로 확인(Polling)하거나 웹소켓(WebSocket)으로 푸시받을 수 있게 합니다.
3. **목록 API 고도화**: 데이터가 쌓였을 때 앱이 버벅이지 않도록 페이지네이션(Pagination)과 검색 기능을 추가합니다.

## Day 29 (월) — FastAPI BackgroundTasks 기반 비동기 큐 도입

> [!TIP]
> 오늘의 목표: 현재 응답을 기다려야 하는 배치 API를, "접수 즉시 응답(202 Accepted)"하고 백그라운드에서 처리하도록 변경합니다.

- **작업 내용**:
  - `POST /api/analyze/batch/async` 엔드포인트 신설.
  - 요청을 받으면 DB에 `status = 'PENDING'`으로 레코드들만 먼저 생성하고, `task_id`를 즉시 반환.
  - FastAPI의 `BackgroundTasks`를 이용해 백그라운드 워커가 순차적으로 LLM을 호출하고 DB 상태를 `DRAFT`로 업데이트.
- **기대 효과**: 사용자는 20장 분석 요청 후 로딩 화면에서 무한정 기다리지 않고 바로 앱을 계속 사용할 수 있습니다.

## Day 30 (화) — 작업 진행 상태 조회 API 구현 (Polling)

> [!TIP]
> 오늘의 목표: 앱에서 백그라운드로 돌아가고 있는 분석의 진행률을 확인할 수 있는 API를 만듭니다.

- **작업 내용**:
  - `GET /api/tasks/{task_id}/status` 엔드포인트 구현.
  - 반환값: `{"total": 20, "completed": 5, "failed": 1, "status": "PROCESSING"}` 형태.
- **기대 효과**: 앱 상단에 "사진 분석 중... (5/20)" 과 같은 프로그레스 바를 띄울 수 있게 됩니다.

## Day 31 (수) — 재시도(Retry) 로직 및 에러 핸들링 강화

> [!TIP]
> 오늘의 목표: OpenAI API 네트워크 오류나 Rate Limit 발생 시, 실패 처리하지 않고 자동으로 재시도하게 만듭니다.

- **작업 내용**:
  - LLM 호출 실패 시 `tenacity` 라이브러리 등을 활용해 Exponential Backoff(지수적 백오프) 방식으로 2~3회 재시도 로직 추가.
  - 최종 실패 시 DB `status`를 `ERROR`로 변경하고, 앱에서 "재시도 버튼"을 누를 수 있도록 에러 사유를 상세 저장.
- **기대 효과**: 네트워크 불안정으로 인한 분석 실패 스트레스를 대폭 줄입니다.

## Day 32 (목) — 결과 목록 API (GET) 페이지네이션 및 필터링

> [!TIP]
> 오늘의 목표: 사용자가 저장한 데이터가 100개, 1000개가 넘어가도 앱이 빠르게 목록을 불러오도록 API를 최적화합니다.

- **작업 내용**:
  - 기존 `GET /api/results`를 수정하여 `page`, `limit` 쿼리 파라미터 지원.
  - 정렬 조건(최신순, 임박순 등) 및 `type` 별 필터링 지원 (`GET /api/results?type=SCHEDULE&sort=expires_asc`).
- **기대 효과**: 앱 스크롤 시 데이터를 20개씩 끊어 불러오는(Infinite Scroll) 부드러운 UI 구현이 가능해집니다.

## Day 33 (금) — 외부 캘린더 연동용 iCal / 딥링크 데이터 포맷팅

> [!TIP]
> 오늘의 목표: 서버에서 추출한 일정을 구글 캘린더나 애플 캘린더에 바로 등록할 수 있는 포맷으로 제공합니다.

- **작업 내용**:
  - SCHEDULE 타입 상세 조회 시, `.ics` (iCalendar) 포맷 텍스트를 함께 반환하거나 앱 딥링크(Intent)에 넣기 좋게 날짜를 ISO8601 포맷으로 엄격하게 정규화.
- **기대 효과**: "캘린더에 추가" 버튼 하나로 일정 등록이 끝나는 매직을 선사합니다.

## Day 34 (토) — WebSocket 실시간 연동 (선택 심화 과제)

> [!WARNING]
> 이 작업은 앱(프론트엔드) 팀과의 협의가 필수입니다. Polling으로 충분하다면 이 단계는 건너뛰어도 좋습니다.

- **작업 내용**:
  - `ws:// /api/ws/analyze` 웹소켓 엔드포인트 오픈.
  - 백그라운드 분석이 1장 끝날 때마다 서버가 앱으로 `{"event": "ITEM_COMPLETED", "id": 12, "type": "PLACE"}`를 실시간 푸시.
- **기대 효과**: 앱에서 계속 API를 찌를(Polling) 필요 없이, 알림 오듯 쏙쏙 리스트가 업데이트됩니다.

## Day 35 (일) — 5주차 통합 테스트 및 최적화

> [!TIP]
> 오늘의 목표: 비동기 큐 환경에서 DB Lock이나 동시성 이슈가 없는지 철저히 점검합니다.

- **작업 내용**:
  - 대량 더미 데이터(50건 이상) 배치 요청 후, 백그라운드 처리 및 상태 조회 테스트.
  - 페이지네이션 쿼리 응답 속도 프로파일링 및 DB 인덱스 추가 확인.

### 💬 논의 필요 사항 (앱 팀과 상의)
- 백그라운드 작업 진행률을 **주기적으로 API를 호출(Polling)** 해서 업데이트할지, 아니면 **웹소켓(WebSocket)** 을 연결해 서버가 푸시해줄지 결정해야 합니다. (우선순위: Polling이 구현은 더 쉽고 안정적입니다.)
- 실패한 항목 처리는 어떻게 할까요? (예: "분석 실패 (재시도 ↻)" UI 추가 여부)
