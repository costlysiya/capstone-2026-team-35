## 2. 연구 목적 및 문제 정의

스마트폰에 문서가 대량 축적되지만, 파일명이나 메타데이터에 의존하는 검색은 문서 내용을 충분히 반영하지 못해 관리와 검색을 어렵게 한다는 문제를 제기한다(1절, p. 1). 또한 개인 문서 또는 그 내용을 서버로 전송해 분류하는 방식은 프라이버시 및 지연시간 문제를 야기할 수 있다고 본다.

이에 저자들은 OCR로 얻은 텍스트 특징과 문서 이미지의 시각 특징을 결합하는 경량 다중모달 분류 파이프라인을 제안하고, 이를 단말에서 실행 가능한 크기로 양자화하였다. 즉, 연구의 직접 목적은 **문서 내용 기반 분류를 단말 내에서 수행하면서 모델 크기와 지연시간을 관리하는 것**이다.

## 3. 핵심 내용

### 연구 방법

- PDF의 첫 페이지만 이미지로 렌더링한 뒤, Google ML Kit로 OCR 텍스트를 추출한다(4절, p. 3-4). 모든 페이지를 처리하면 지연시간이 커진다는 이유로 첫 페이지만 사용하였다.
- 텍스트 경로는 OCR 결과에 정규식 필터링, 비영어 토큰 제거, TF-IDF 벡터화, Truncated SVD 차원 축소를 적용하고, 완전연결층과 softmax로 분류한다(3.1절 및 4절, p. 2-4).
- 이미지 경로는 사전학습 MobileNet에 pooling 및 dense layer를 결합해 특징을 산출한다(3.1절, p. 3).
- 두 경로의 pre-softmax 특징을 결합하는 late fusion을 사용하였다. 결합 방식으로 concatenation, average, max, highway layer를 비교했으며, 개별 모달리티도 독립 분류할 수 있게 설계하였다(3.2절, p. 3).

### 데이터와 실험 환경

- 다중모달 구조의 일반 성능 검증에는 레시피 텍스트와 음식 이미지가 함께 있는 UPMC Food-101을 사용했다. 약 10만 이미지, 101개 음식 범주 데이터이다(3절, p. 2).
- 실제 문서 분류 검증에는 내부 조사로 정한 Travel 118건, Personal information 100건, Receipts 98건, Papers/books 102건, Misc 94건으로 구성된 약 512건의 자체 PDF 데이터셋을 사용했다(표 3, p. 3).
- 영어만 대상으로 하며, 문서 데이터는 PDF 및 첫 페이지로 제한했다(4절, p. 3-4).

### 주요 기술·결과·결론

- Food-101에서 concatenation fusion은 정확도 89.8%, 모델 크기 13 MB를 기록했다. 표 1의 비교에서 텍스트 SVD 모델은 85.39%/40 MB, 이미지 모델은 66.1%/17 MB였고, 비교 대상 다중모달 선행 모델보다 작은 크기로 제시되었다(표 1, p. 2).
- 자체 문서 데이터셋에서 텍스트 단독 Top-1 정확도는 59.62%, 시각 단독은 71.88%, 텍스트+시각 결합은 84.38%였다(표 4, p. 4). 이 결과는 해당 데이터셋에서 두 특징을 결합했을 때 단일 특징보다 높은 분류 정확도를 보였다는 근거이다.
- TFLite 사후 양자화는 약 0.5%p 정확도 감소와 75% 모델 압축을 가져왔고, 최종 모델은 약 13 MB였다. 문서당 전체 파이프라인 실행시간은 4.6초이며 이 중 OCR이 3.5초를 차지했다(4절, p. 4).
- 저자들은 자체 문서 데이터셋 크기가 충분하지 않아 결론적 증거가 되기 어렵다는 한계를 명시한다(5절, p. 4).

## 4. 우리 졸업과제와의 연관성

| 관점 | 실제 연관성 | 논문 근거와 프로젝트 해석 |
|---|---|---|
| OCR / 이미지 기반 정보 추출 | 높음 | **논문:** OCR 텍스트와 PDF 렌더링 이미지를 함께 사용해 문서를 분류한다(4절). **프로젝트 해석:** 소생 앱도 스크린샷의 OCR 텍스트와 이미지 기반 단서로 카테고리를 판단하므로, OCR 단독보다 이미지·텍스트를 함께 고려하는 분류 설계의 선행 근거로 활용할 수 있다. 단, 이 논문은 필드 추출이 아니라 문서 분류를 평가했다. |
| LLM을 활용한 비정형 데이터 구조화 | 해당 없음 | 논문은 LLM 기반 구조화 추출을 다루지 않는다. |
| 온디바이스 처리와 클라우드/LLM 처리의 역할 분리 | 부분적 연관 | **논문:** 개인정보와 지연시간 문제를 이유로 문서 분류를 단말에서 수행한다(1절). **프로젝트 해석:** 소생 앱의 1차 온디바이스 OCR·분류 역할을 설명할 수 있으나, 논문은 클라우드 LLM과의 2단계 분담을 실험하지 않았다. |
| 정확도 / Precision / Recall / F1 | 부분적 연관 | 논문은 분류의 Top-1 accuracy를 보고한다(표 4). Precision, Recall, F1은 이 논문의 실제 문서 실험 결과로 제시되지 않았으므로 소생 앱의 필드별 P/R/F1 평가 근거로 인용해서는 안 된다. |
| 처리 속도 및 비용 | 부분적 연관 | **논문:** 단말 전체 처리 4.6초, 이 중 OCR 3.5초를 보고한다(4절). 비용 비교나 LLM 비용은 보고하지 않는다. 프로젝트의 0.17 ms Regex, 1.32초 LLM, API 비용은 프로젝트 실험 결과로 별도 제시해야 한다. |
| 구조화된 데이터 저장 | 해당 없음 | 문서 분류 파이프라인이 주제이며 SQLite/JSON 등 저장 스키마는 다루지 않는다. |
| 모바일/온디바이스 환경 | 매우 높음 | Android PdfRenderer, Google ML Kit, TensorFlow Lite 양자화로 단말 실행 가능성을 제시한다(4절). |
| 개인정보 및 데이터 보안 | 부분적 연관 | 단말 처리로 문서·내용의 서버 전송을 피함으로써 프라이버시를 보존한다는 문제의식을 제시한다(초록 및 1절). 암호화, 민감정보 탐지, E2EE의 구현·평가는 없다. |
| 확장 가능한 아키텍처 | 낮음 | PDF 외 Word, Excel 등으로 확장 가능하다고 언급하지만 실험은 PDF만 수행했다(4절, p. 3). 데이터 저장·서버 확장성은 검증하지 않았다. |

## 5. 최종보고서에서 사용할 수 있는 핵심 근거

1. **논문의 주장:** 자체 문서 데이터에서 텍스트 및 시각 특징의 결합 모델은 Top-1 정확도 84.38%로, 텍스트 단독(59.62%)과 시각 단독(71.88%)보다 높았다.  
   **원문 위치:** 표 4, 4절, p. 4.  
   **프로젝트 적용:** OCR 텍스트만을 절대적 근거로 삼지 않고 스크린샷 이미지의 시각 단서를 함께 고려하는 1차 분류 설계의 근거로 사용한다. 단, 소생 앱의 정확도와 직접 비교하거나 동일 수치가 재현된 것처럼 쓰면 안 된다.

2. **논문의 주장:** 개인 문서 또는 내용의 서버 전송은 프라이버시와 지연시간 문제를 유발할 수 있으므로, 경량 아키텍처로 문서를 단말에서 분류하고자 했다.  
   **원문 위치:** 초록 및 1절, p. 1.  
   **프로젝트 적용:** 원본 스크린샷과 주 저장 데이터를 단말에 보관하고, 1차 분류를 단말에서 수행하는 설계 배경에 사용할 수 있다. 암호화나 무결성 보장 근거로 확대하지 않는다.

3. **논문의 주장:** 사후 양자화는 약 0.5%p의 정확도 감소와 75% 모델 압축을 보였으며, 최종 모델 크기는 약 13 MB였다.  
   **원문 위치:** 4절 ‘On-Device Execution’, p. 4.  
   **프로젝트 적용:** 모바일 배포에서는 정확도뿐 아니라 모델 크기와 지연시간을 함께 평가해야 한다는 측정 관점의 근거로 사용한다. 소생 앱이 동일 양자화를 적용했다는 뜻으로 쓰지 않는다.

4. **논문의 주장:** 전체 처리시간 4.6초 중 OCR이 3.5초를 차지했다.  
   **원문 위치:** 4절 ‘On-Device Execution’, p. 4.  
   **프로젝트 적용:** OCR이 모바일 문서 처리의 주요 지연 요인이 될 수 있으므로, 프로젝트에서 OCR·분류·LLM을 분리 측정한 이유를 설명하는 데 적합하다. 기기와 OCR 엔진이 다르므로 절대 시간값 비교 근거는 아니다.

## 6. 최종보고서용 서술문

Garg, Harichandana, and Kumar(2021)는 모바일 단말에 축적된 문서를 서버로 전송하지 않고 관리하기 위한 온디바이스 문서 분류 파이프라인을 제안하였다. 해당 연구는 OCR로 추출한 텍스트 특징과 문서 이미지의 시각 특징을 late fusion 방식으로 결합하였으며, 자체 문서 데이터셋에서 결합 모델의 Top-1 정확도는 84.38%로 텍스트 단독 59.62%, 시각 단독 71.88%보다 높게 나타났다[Garg et al., 2021]. 이는 문서 또는 스크린샷의 범주 판단에서 OCR 텍스트만이 아니라 시각적 구성도 보조 정보가 될 수 있음을 보여준다.

본 프로젝트는 위 연구의 온디바이스 처리 원칙과 다중 단서 활용 방식을 참고하여, 스크린샷을 단말에서 우선 OCR·분류하고 이후 필요한 정보만 후속 처리 대상으로 선정하도록 설계하였다. 다만 선행연구의 대상은 영어 PDF 문서 및 5개 문서 범주이고, 본 프로젝트의 대상은 사용자 스크린샷과 자체 카테고리이므로, 해당 정확도 수치를 본 프로젝트 성능의 근거로 일반화하지 않았다. 또한 선행연구가 제시한 OCR 중심 지연시간 측정 관점을 참고하되, 본 프로젝트의 성능은 별도의 자체 실험으로 보고하였다.

## 2. 연구 목적 및 문제 정의

이 논문은 OCR 결과에 문자·단어·문서 구조 수준의 오류가 남으면, 이후 검색·질의응답·정보추출에서 오류가 누적될 수 있다고 문제를 정의한다(2.1절, p. 2; 3절, p. 3). 기존 Document AI가 질의응답이나 추론 과업에 집중하여 OCR 텍스트를 구조화된 정보 자산으로 보존·관리하는 중간 단계를 충분히 다루지 못했다고 본다(2.2절, p. 3).

저자들은 OCR 오류를 체계적으로 교정하여 구조적으로 일관된 텍스트를 복원하고, 이를 데이터베이스 또는 지식베이스에서 활용할 수 있게 하는 REVISE를 제안한다. 별도의 대규모 OCR 오류 정답 데이터를 확보하기 어렵다는 문제에는 공개 코퍼스에 현실적 오류를 주입하는 synthetic data contamination 전략으로 대응한다.

## 3. 핵심 내용

### 연구 방법

- OCR 오류를 문자 수준(삽입, 삭제, 치환, 전치), 단어 수준(과분절, 과소분절), 열 수준(column reading order)으로 분류하는 계층적 taxonomy를 제시했다(표 1, 3.1절, p. 3-4).
- 깨끗한 텍스트에 다단 열 읽기 순서 오류, 문자·단어 오류를 주입해 오염 코퍼스를 만들고, 이를 원문으로 복원하도록 학습한다(3.2절, p. 4; 표 6, p. 11).
- REVISE meta는 6개 오류 유형 전체를 학습하며, 6개 보조 모델은 오류 유형별로 학습한다. 모든 모델의 backbone은 Llama-3.1-1B-Instruct이고, Wikipedia에서 샘플링한 합성 데이터 각 30,000건을 사용했다(3.3절, p. 4).

### 데이터·실험 환경과 평가

- OCR 텍스트는 주로 EasyOCR로 문서 이미지에서 추출했다. DUDE는 제공된 OCR 텍스트를 사용했다(부록 B, p. 11).
- 검색은 VisualMRC·DUDE에서 Recall@1/3/5, 문서-질의 유사성은 DocVQA·CORD·FUNSD에서 BERTScore, 질의응답은 VisualMRC에서 CIDEr, CORD에서 F1으로 평가했다(4.2절, p. 5).
- 검색에는 bge-large-en-v1.5, e5-large-v2, jina-embeddings-v2-base-en, gte-base-en-v1.5를, 질의응답에는 Gemma-2-2B-it와 Llama-3.1-8B-Instruct를 사용했다(4.1절, p. 5). 학습은 4대의 NVIDIA A6000 GPU에서 수행했고, 추론에는 단일 가속기를 사용했다(부록 B, p. 11).

### 핵심 실험 결과와 결론

- REVISE meta의 검색 평균 Recall은 VisualMRC에서 0.6578에서 0.6666으로, DUDE에서 0.2534에서 0.2975로 증가했다. 저자 본문은 두 데이터셋에서 평균 Recall이 각각 1.3%, 17.3% 향상했다고 서술한다(표 2, p. 5; 5.1절, p. 6).
- BERTScore는 DocVQA 0.4959→0.5137, CORD 0.5390→0.5443, FUNSD 0.5577→0.5647로 상승했다(표 3, p. 6).
- QA 평가에서 VisualMRC의 CIDEr는 Gemma 320.9→329.2, Llama 290.7→293.1이었고, CORD F1은 Gemma 0.367→0.372, Llama 0.448→0.450이었다(표 4, p. 6). 본문은 각각의 상대 향상도도 함께 제시한다.
- 오류별 모델은 상황에 따라 baseline보다 낮아질 수 있으며, 이는 오류가 거의 없는 입력에 불필요한 수정이 새 오류를 만들 수 있는 over-correction 때문이라고 저자들이 명시한다(5.1절, p. 6). 
- 한계로 산업 특화 문서·희귀 오류에 대한 검증 부족, 표·차트·수식 등 혼합 콘텐츠 미지원, LLM 기반 정성평가의 편향 가능성, 오염 비율의 포괄적 통계 분석 부족을 열거한다(Limitations, p. 7-8).

## 4. 우리 졸업과제와의 연관성

| 관점 | 실제 연관성 | 논문 근거와 프로젝트 해석 |
|---|---|---|
| OCR / 이미지 기반 정보 추출 | 높음 | **논문:** OCR 오류가 이후 key extraction, NER, 검색에 전파될 수 있다고 설명하고, 문자·분절·열 순서 오류를 분류한다(3.1절). **프로젝트 해석:** 스크린샷 OCR 결과를 후속 필드 추출에 사용하기 전에 품질 관리가 필요하다는 이론적 근거이다. 논문은 소생 앱의 OCR 엔진이나 한국어 OCR 정확도를 평가하지 않았다. |
| LLM을 활용한 비정형 데이터 구조화 | 보통 | **논문:** OCR+LLM 방식이 OCR 오류를 상속할 수 있으며, 구조화 OCR 출력을 DB/지식베이스에 활용하는 task-independent framework를 지향한다(2.2절 및 3절). **프로젝트 해석:** OCR 텍스트를 LLM으로 구조화하기 전 오류 보정·불확실성 처리가 중요하다는 근거이다. REVISE 자체는 JSON schema 또는 Pydantic structured output을 평가하지 않았다. |
| 온디바이스 처리와 클라우드/LLM 처리의 역할 분리 | 해당 없음 | 제안 모델 학습·추론은 GPU 가속 환경이며, 모바일 배포·온디바이스/클라우드 분할을 다루지 않는다. |
| 정확도 / Precision / Recall / F1 | 보통 | 검색 Recall@K와 CORD QA F1을 사용한다(표 2·4). OCR 문자 정확도나 프로젝트 필드 추출 Precision/Recall/F1을 직접 보고하지는 않는다. |
| 처리 속도 및 비용 | 해당 없음 | 지연시간, API 비용, 모바일 자원 사용량을 비교·보고하지 않는다. |
| 구조화된 데이터 저장 | 보통 | 구조적으로 복원한 OCR 출력을 DB 또는 지식베이스에 쓸 수 있다고 명시한다(2.2절, p. 3; 결론, p. 7). 구체적 DB 스키마나 저장 성능은 제시하지 않는다. |
| 모바일/온디바이스 환경 | 해당 없음 | 단일 가속기 추론 환경이지만 모바일 장치 실험은 없다(부록 B). |
| 개인정보 및 데이터 보안 | 해당 없음 | 표 7의 프롬프트는 개인정보 보존을 지시할 뿐(부록 C, p. 12), 개인정보 탐지·마스킹·암호화·보안 평가를 수행하지 않는다. 이를 개인정보 보호 근거로 인용하면 안 된다. |
| 확장 가능한 아키텍처 | 부분적 연관 | 오류 taxonomy와 합성 오류 주입을 통해 다양한 오류를 다루려 하나, 저자 스스로 산업 특화 문서 및 혼합 콘텐츠 검증의 한계를 밝힌다(Limitations, p. 7-8). |

## 5. 최종보고서에서 사용할 수 있는 핵심 근거

1. **논문의 주장:** OCR 오류는 키 추출, 개체명 인식, 정보 검색 등 후속 NLP 과업에 누적 전파될 수 있다.  
   **원문 위치:** 3절 및 3.1절, p. 3.  
   **프로젝트 적용:** OCR 결과를 곧바로 확정 저장하지 않고, 사용자 검토 및 후속 구조화 단계로 연결하는 설계의 필요성을 설명할 수 있다. 단, 이 근거만으로 소생 앱의 오류율이 낮아졌다고 주장할 수는 없다.

2. **논문의 주장:** OCR 오류는 문자 수준의 삽입·삭제·치환·전치, 단어 수준의 과/과소분절, 열 수준의 읽기 순서 오류로 체계화할 수 있다.  
   **원문 위치:** 표 1 및 3.1절, p. 3-4; 그림 1, p. 1.  
   **프로젝트 적용:** OCR 오류 사례 분석과 테스트셋 설계에서 오류 유형을 구분하는 기준으로 사용한다. 한국어 조사·띄어쓰기, 캡처 UI 특유의 오류가 모두 포괄된다고 단정하지 않는다.

3. **논문의 주장:** REVISE meta 적용 후 검색 평균 Recall은 VisualMRC 0.6578→0.6666, DUDE 0.2534→0.2975로 증가했으며, CORD QA F1도 두 LLM에서 상승했다.  
   **원문 위치:** 표 2, p. 5; 표 4 및 5.1-5.2절, p. 6.  
   **프로젝트 적용:** OCR 후처리 품질이 검색·질의응답처럼 OCR 이후의 정보 활용 성능과 관련될 수 있다는 실증 근거로 사용한다. 소생 앱의 날짜·가격·장소명 추출 성능 또는 LLM structured output의 개선률로 바꾸어 인용해서는 안 된다.

4. **논문의 주장:** 오류 유형별 교정은 데이터의 오류 분포와 맞지 않을 때 과교정으로 baseline보다 성능이 낮아질 수 있다.  
   **원문 위치:** 5.1절, p. 6.  
   **프로젝트 적용:** LLM 후처리 결과를 자동 확정하지 않고 사용자가 수정·승인할 수 있게 하는 UX, 그리고 실제 스크린샷 기반 검증의 필요성을 뒷받침한다.

5. **논문의 주장:** 구조적으로 복원된 OCR 출력은 구조화된 문서 DB 및 정보 관리에 활용될 수 있으나, 산업 특화 문서와 표·차트·수식 혼합 콘텐츠에는 한계가 있다.  
   **원문 위치:** 2.2절·3절, p. 3; 결론 및 Limitations, p. 7-8.  
   **프로젝트 적용:** 추출 결과를 JSON 형태로 저장하는 설계의 개념적 배경으로 활용할 수 있다. SQLite JSON 구조의 유효성, 보안성, 확장성은 프로젝트 설계와 실험으로 별도 설명해야 한다.

## 6. 최종보고서용 서술문

Shim, Hong, and Lim(2026)은 OCR 결과에 포함된 문자 치환·삭제·삽입, 단어 분절, 다단 문서의 읽기 순서 오류가 후속 정보추출과 검색·질의응답의 성능을 저해할 수 있음을 지적하고, 이를 문자·단어·구조 수준에서 교정하는 REVISE 프레임워크를 제안하였다[Shim et al., 2026]. 공개 코퍼스에 현실적 오류를 주입해 학습한 REVISE meta는 VisualMRC와 DUDE에서 검색 Recall을, DocVQA·CORD·FUNSD에서 BERTScore를 향상시켰으며, CORD 질의응답 F1도 두 평가 LLM에서 소폭 개선하였다[Shim et al., 2026]. 이 결과는 OCR 출력의 품질 관리가 후속 정보 활용 품질과 관계될 수 있음을 보여준다.

본 프로젝트에서는 OCR 텍스트가 날짜·가격·장소명 등 구조화 필드의 입력이 되므로, OCR 오류가 후속 결과에 영향을 줄 수 있다는 선행연구의 문제의식을 반영하였다. 이에 추출 결과를 자동 확정값이 아닌 사용자 검토 가능한 초안으로 취급하고, 비정형 필드는 LLM 기반 구조화 단계에서 보강하도록 구성하였다. 다만 REVISE는 영어 중심 공개 문서 데이터와 검색·질의응답 과업에서 평가된 사전공개 연구이며, 모바일 환경·한국어 스크린샷·JSON 스키마 추출·개인정보 보호를 직접 검증하지 않았다. 따라서 본 프로젝트의 필드별 정확도와 보안성은 자체 실험 및 설계 명세로 별도 제시하였다.

## 종합 시사점 및 아키텍처 설계 판단의 논리적 흐름

## A. 우리 프로젝트를 뒷받침하는 선행연구의 핵심 흐름

두 연구는 다음과 같은 연속된 문제 흐름을 제시한다.

1. 모바일 기기에 문서·이미지가 축적되고, 파일명만으로는 내용 기반 관리가 어렵다.
2. OCR은 문서 이미지를 검색·분류 가능한 텍스트로 바꾸지만, 텍스트만으로는 문서의 시각적 구성 정보를 잃을 수 있으며 OCR 오류도 발생한다.
3. Garg et al. (2021)은 텍스트와 시각 특징을 결합하고, 단말에서 실행하도록 경량화하여 1차 문서 분류를 수행한다.
4. Shim et al. (2026)은 OCR 오류가 후속 검색·질의응답에 전파될 수 있음을 보이고, 오류 보정 후 구조적으로 일관된 텍스트를 정보 시스템에서 활용하는 방식을 제시한다.
5. 본 프로젝트는 이 흐름을 스크린샷 관리에 적용하여, 단말의 OCR·분류와 서버 LLM의 비정형 필드 구조화를 역할별로 배치하고, 결과를 사용자 검토 후 로컬 구조화 데이터로 보존한다.

마지막 단계인 ‘온디바이스 분류 + 선택적 서버 LLM + SQLite JSON 저장’의 결합과 성능은 위 두 논문이 직접 검증한 결과가 아니라 본 프로젝트의 설계 및 자체 실험 결과로 구분해야 한다.

## B. 기존 연구와 우리 프로젝트의 차별점

|---|---|---|---|
| 주된 과업 | 온디바이스 문서 범주 분류 | OCR 텍스트 오류 교정과 검색·QA 개선 | 스크린샷 분류, 정보 추출, 구조화 저장 및 관리 |
| 입력·대상 | 영어 PDF 첫 페이지, 5개 문서 범주 | 공개 문서 데이터의 OCR 텍스트 | 사용자 스크린샷의 OCR 텍스트와 앱 카테고리 |
| 단말 처리 | Android, ML Kit, TFLite 양자화 | 모바일 실험 없음 | 단말 1차 처리 후 선택적 LLM 보강 |
| LLM 역할 | 사용하지 않음 | OCR 후처리 모델 및 QA 평가 | 비정형 필드의 구조화 추출 |
| 저장 | 구체 DB 구조 미제시 | DB/지식베이스 활용 가능성을 제시 | 로컬 SQLite의 가변 JSON 필드와 이미지 파일 매핑 |
| 보안 | 서버 전송 회피의 문제의식 | 직접 평가 없음 | 민감정보 사전 처리와 로컬 주 저장을 별도 설계·검증 대상으로 둠 |

차별점은 선행연구보다 성능이 우월하다는 주장이 아니라, 서로 다른 선행연구의 문제의식을 **사용자 스크린샷의 관리 흐름**에 맞게 통합했다는 데 있다. 즉, 선행연구의 분류·OCR 후처리 관점을 참고하여 실제 앱에서는 ‘즉시성 요구가 큰 1차 처리’와 ‘문맥 이해가 필요한 구조화 처리’를 분리하고, 사용자 확인 및 로컬 저장까지 연결한 것이다.

## D. 실제 보고서에 인용하기 좋은 논문 TOP 3

분석 대상이 2편이므로 실제 순위는 다음과 같이 2편만 제시한다. 두 편만으로 ‘TOP 3’를 구성하면 존재하지 않는 논문을 추가하는 것이므로 적절하지 않다.

1. **Garg et al. (2021)**: 모바일 단말의 OCR·이미지 결합 분류, 프라이버시·지연시간 고려라는 프로젝트의 핵심 설계와 가장 직접적으로 연결된다.
2. **Shim et al. (2026)**: OCR 오류가 후속 정보 활용에 미치는 영향과 과교정 위험을 설명하는 데 유용하다. 다만 preprint임을 명시한다.

## 최종 작성 시 유의사항

- 프로젝트 성능(예: Field-level Precision/Recall/F1, Regex·LLM 지연시간·비용)은 `ondevice_vs_llm_comparison_report_v2.md`의 조건과 함께 **자체 실험 결과**로 제시한다. 이 수치를 두 선행연구의 검증 결과처럼 서술하지 않는다.
- Garg et al. (2021)의 수치는 영어 PDF 첫 페이지만으로 수행한 문서 분류 정확도이며, 필드 추출 정확도가 아니다.
- Shim et al. (2026)의 수치는 공개 영어 문서 데이터에서 검색·질의응답으로 평가한 결과이고, arXiv preprint이다. 한국어 스크린샷, 모바일 성능, 개인정보 보호 효과에 대한 직접 근거는 아니다.
- 개인정보 마스킹·암호화·로컬 SQLite JSON 저장·서버 캐시는 본 프로젝트의 설계 근거와 구현 명세로 설명하고, 필요하면 해당 주제를 직접 검증한 별도 보안·데이터 관리 선행연구를 추가하는 것이 학술적으로 타당하다.
